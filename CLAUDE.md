# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Run against a local/dev cluster
cargo run -- -u http://localhost:9200

# Build
cargo build            # debug
cargo build --release  # release

# Test (all tests are unit tests colocated in `#[cfg(test)] mod tests` blocks)
cargo test

# Performance harness for the indices panel at 50k indices (never runs in CI)
cargo test --release perf -- --ignored --nocapture
cargo test test_selection_movement       # single test by name
cargo test app::filter::tests            # a module's tests (binary crate: no --lib)

# Lint / format — CI runs these with zero tolerance for warnings/diffs
cargo clippy --all-targets -- -D warnings   # test code included
cargo fmt --all -- --check
cargo fmt --all         # apply formatting
```

CI (`.github/workflows/ci.yml`) runs `cargo check`, `cargo test`, `cargo fmt --all -- --check`, and `cargo clippy --all-targets -- -D warnings` as separate jobs on every push/PR to `main`. A change isn't done until all four pass.

## Architecture

EstiCLI is a `top`-like ratatui TUI that polls Elasticsearch on a timer and renders indexing rates. The whole app runs on a single-threaded event loop in `main.rs`; concurrency is limited to two background fetch tasks that report back over channels.

### Event loop (`main.rs`)

`run()` is a tight loop: poll async results (non-blocking) → tick spinner → draw → poll keyboard (50ms timeout) → maybe start a new fetch. There is no dirty-tracking — every iteration redraws unconditionally. `map_key_to_action()` translates a `KeyEvent` into an `app::actions::Action`; popups (`help_popup`, `details.show_popup`) and filter-input mode each get their own key-mapping branch checked in priority order before the default keymap. `Action` is a plain data enum (some variants carry values, e.g. `SelectPageUp(usize)`) dispatched through `App::handle_action` — this indirection exists so key bindings and behavior stay decoupled and testable without a terminal.

Page-scroll sizes (`SelectPageUp/Down`, `DetailsScrollPageUp/Down`) are computed fresh each loop iteration from the *actual* rendered geometry (`ui::table_page_size`, `ui::details_popup::visible_rows`) rather than hardcoded — see "Layout" below for why this must stay in sync with `ui::compute_areas`.

### App state (`app/mod.rs`)

`App` owns all state and is passed by reference into every UI widget (read-only) and mutated only via `Action` handlers. Sub-concerns are split into their own state structs, each with delegating methods on `App`: `SortState` (`app/sort.rs`), `FilterState` (`app/filter.rs`), `DetailsState` (`app/details.rs`), `SnapshotState` (`app/snapshot.rs`).

**Visibility filtering is centralized.** `App::is_visible()` is the single predicate (exclusions + system-index toggle + name/jq filter — the filter only while the indices panel is the one in the main area, since the same box filters nodes on the nodes panel and a node-name filter must not zero the header rate) that both `filtered_indices()` and `visible_summary()` delegate to — never reimplement this filter inline. `visible_summary()` computes the filtered index list *and* aggregated `ClusterMetrics` (total rate, total bytes/sec) in one pass; `ui::draw()` calls it once per frame and threads the result into every widget that needs it (header, table, footer) instead of each widget re-filtering independently. When adding a new widget that needs the visible set, take it as a constructor argument rather than calling `app.filtered_indices()` inside `render()`.

**The main panel holds one of two tables.** `App.show_main_panel` controls whether the panel is on screen at all (`3`); `App.main_panel: MainPanel` (`Indices` | `Nodes`, toggled with `n`) controls which table it holds. They are alternatives occupying the same `Areas::table` rect, not stacked panels. Navigation, sorting and scroll offset all dispatch on `main_panel` — `select_up`/`next_column`/etc. act on the focused panel only, and each panel keeps its own cursor (`selected_name` / `selected_node`), sort state (`sort` / `node_sort`) and offset (`table_offset` / `node_table_offset`) so switching preserves both. When adding a panel-scoped behavior, extend the dispatch rather than reading `main_panel` inside a widget.

**`_nodes/stats` is only requested while its panel is focused.** `App::nodes_focused()` gates the request in `start_fetch()`, and `FetchPayload.nodes` is `Option`: `None` means "not requested, keep what's on screen", which is deliberately distinct from `Some(vec![])` ("the cluster reported no nodes"). The indices and health requests stay unconditional because the header rate and cluster graph are driven by them regardless of which panel is showing. `EsClient::fetch_tick(want_nodes)` joins all three.

**The snapshot baseline is fixed, not rolling.** `SnapshotState` (`app/snapshot.rs`) freezes both panels' metrics when `s` is pressed, and every later tick is compared against *that* frozen moment rather than against the previous tick — which is the whole point, and the thing to preserve if this code is touched. `capture()` takes the baseline; `observe()` runs once per successful `poll_fetch_result` to reconcile it with the cluster, adopting a first reading for rows that appeared since (there is no honest comparison against a moment they didn't exist in) and dropping indices that vanished — but *keeping* node baselines for nodes missing from a reading, since a restarting node drops out for a tick before it rejoins and its baseline is what lets the comeback show `⟲`. `capture()` only takes node readings when the nodes panel is focused (`App::take_snapshot`); otherwise they are whatever the panel showed last time it was open, and the node half is left for `observe()` to fill in. `observe()`'s `nodes: Option<&[NodeStats]>` carries the same `None` vs `Some(vec![])` distinction as `FetchPayload.nodes` — `None` must leave the node baseline alone, and it is also why a snapshot taken before the nodes panel was ever focused still works: the node half fills in on the first fetch that requests it. With no snapshot active every trend comes back `Unchanged` and the tables render as if the feature didn't exist. Comparison cost is deliberately split: `observe()` is the only part that scales with the cluster (~2.5ms at 50k indices) and it sits on the refresh tick, while the render path does one hash lookup per *on-screen* row and measures as free against the render it was already doing.

**Selection is tracked by index name, not by row position.** `App.selected_name: Option<String>` is the cursor; the row it lands on is derived on demand via `selected_position_in(&visible)` (or `selected_position()`, which filters first). This is deliberate: the list is re-sorted on every refresh tick, so a `selected_index: usize` would silently slide onto a different index between polls. Anything acting on the selection should resolve it by name rather than by indexing into `filtered_indices()`. A selection that is merely filtered out is kept (so it returns when the filter is cleared) — only `clamp_selection()`, called after each successful refresh, drops it, and only when the index has actually disappeared from the cluster.

**Filter mode compiles down to two different representations, deliberately.** `FilterState::recompile()` (`app/filter.rs`) produces either a `regex_lite::Regex` (default, `/`) matched directly against `.name`, or a compiled jq `select(...)` filter (`//`, toggled while the input is empty) matched against the full serialized index. A pattern containing no regex metacharacters skips the regex engine entirely and is matched with `str::contains`, which is exactly equivalent (`Regex::is_match` is unanchored) and ~70x faster over 50k names; keep that shortcut strictly limited to metacharacter-free patterns, since anchors and classes change what matches. This split exists because jq's `test()` builtin recompiles its regex argument from scratch on *every call* — routing plain name search through `select(.name | test(...))` would mean recompiling the same regex once per index on every redraw (measured ~28x slower on 5k indices). Never route the common name-search case through jq's `test`/`match` for this reason; only jq mode should touch `jaq_core`/`serde_json` per match. jq programs are compiled behind `JQ_PRELUDE`, which shadows `halt`/`halt_error` (they `std::process::exit`, leaving the terminal raw) and `stderr` (writes over the TUI); they're shadowed rather than removed because jaq's std defines `halt_error/0` in terms of the native. The compile-time probe runs against both an index-shaped and a node-shaped row and accepts a program that works on either, since one box filters both panels.

**Filter box input goes through `FilterState::handle_key`, not raw `tui_input` calls.** It only calls `recompile()` when `tui_input`'s `StateChanged.value` is true — cursor-only movement (arrows, Home/End, word-jumps) reports `value: false` and is intentionally cheap, so navigating the box stays instant regardless of how expensive the current filter is to (re)compile. It also drives the filter's cursor blink (`cursor_visible()`, rendered in `ui/table.rs`) off its own `Instant`-based clock rather than the terminal's SGR blink attribute, which most modern terminal emulators ignore.

**Rate calculation is a two-stage average.** `stats::RateTracker` (owned by `App` as `Arc<std::sync::Mutex<RateTracker>>`) holds the previous `_stats` reading, keyed by index name, and `rates_from_snapshot()` turns each new reading into a raw docs/sec sample per index — `Option<f64>`, `None` where there is no honest sample (first reading, an index seen for the first time, a counter that went backwards, a tick where no primary answered). `App::update_indices_with_rates()` then smooths the samples over a rolling window (`--rate-samples`, per-index `VecDeque<f64>` in `index_rate_history`), skipping `None` rather than averaging in a fake 0. The cluster-wide rate graph (`rate_history: VecDeque<f64>`, capped at `MAX_HISTORY_POINTS` = 300 — one sample per terminal column) records the total of the visible set each successful tick.

**Data-stream backing indices are not system indices.** `is_system_index()` treats dot-prefixed names as system *except* `.ds-<stream>-…`/`.fs-<stream>-…`, which hold user data (most ingestion on Agent/Logstash/OTel clusters). Default `_stats` already omits hidden system data streams.

**Background fetches use mpsc, not shared mutable state.** `EsClient` is stateless and `Clone` (reqwest's client is reference-counted), so `App::start_fetch()` spawns a task with its own clone, calls `EsClient::fetch_tick(want_nodes)`, locks the `RateTracker` only *after* the requests are back (never across an `.await`), and sends a `FetchPayload` down `fetch_tx`. `fetch_tick` `tokio::join!`s `_stats`, `_cluster/health` and (when the nodes panel is focused) `_nodes/stats` and returns each as its own `Result` in a `Tick`: `App::apply_fetch()` applies whatever succeeded and joins the failures into `App.error`, so a 403 on `_cluster/health` or one slow node never stops the indices table, header rate and graph. Keep new polling requests independent in the same way. `poll_fetch_result()` drains `fetch_rx` non-blockingly each loop tick; `refetch_pending` queues a fetch behind an in-flight one when something needs fresh data now (switching to the nodes panel mid-fetch). `DetailsState` follows the same pattern with its own channel pair and its own `EsClient` clone — it never waits behind polling — initially triggered by `Enter` and then kept alive: `App::refresh_open_details()` (called after every tick whose `_stats` succeeded) re-fetches the open popup's index by name. Results are tagged with the index name, and `poll()` drops one that doesn't match the popup now on screen (a fetch still in flight when the popup was closed and reopened on another index). `DetailsState::fetch()` distinguishes "opening a new index" (resets `data`/`scroll`/`loading`) from "refreshing the same one already on screen" (leaves them untouched, with `refreshing` driving a small in-title indicator) — and refuses to start a second fetch while one's still in flight. Don't block the render loop waiting on either channel.

### Elasticsearch layer (`elasticsearch/`)

`EsClient` (`client.rs`) wraps `reqwest` with a `send_json<T>` helper that maps non-2xx responses to `EstiCliError::Api` (body cut down to Elasticsearch's `reason`, or truncated). **Build every URL with `EsClient::endpoint(&[segments])`, never `base_url.join(...)`**: it appends percent-encoded path segments, which keeps a gateway path prefix (`https://gw/es`) and sends index names with `%`, `&`, `#` or non-ASCII characters intact; `join` silently replaced the prefix's last segment. Polling requests carry a `filter_path` (`STATS_FILTER_PATH`, `NODES_FILTER_PATH`) naming exactly the leaves the app reads — about 8x less to build, send and parse — and the wire types default every field, so one odd entry (7.x has no per-index `health`; an index whose primaries didn't answer) never fails the whole response. `stats.rs` handles the polling path (`_stats`, `_cluster/health`); `details.rs` handles the on-demand path (`fetch_index_details`), which fans out 7 parallel requests via `tokio::join!` (settings, ILM explain, segments, cat/shards, index templates, cat/indices, data streams) and degrades each field independently with `.unwrap_or_default()`/`.ok()` rather than failing the whole popup if one sub-request errors. Response shapes live in `types.rs`, deliberately mirroring ES's JSON rather than the app's internal `models.rs` structs — conversion happens explicitly in `stats.rs`/`details.rs`, keeping wire format decoupled from what the UI consumes.

### UI layer (`ui/`)

`ui::compute_areas()` is the one place that knows the screen layout (header / graph+health / table / footer, with graph+health further split horizontally); it's used both by `draw()` for rendering and by `main.rs` for computing page-scroll sizes, so they can't drift apart. Each widget module (`header.rs`, `table.rs`, `footer.rs`, `chart.rs`, `health.rs`, `details_popup.rs`, `help_popup.rs`) implements ratatui's `Widget`/`StatefulWidget` and takes `&App` (plus any precomputed data like `ClusterMetrics` or the filtered index slice) as constructor arguments — no widget mutates state. `chart.rs` draws the rate history as a filled area graph, using partial block glyphs for eight vertical steps per terminal row and one sample per column (which is why `MAX_HISTORY_POINTS` has to exceed a wide terminal's width); its `column_eighths()` height math is a free function precisely so it can be unit-tested without a terminal. Colors driven by data (table gradient, chart, health status) go through `Colormap::color_at()` (`ui/types.rs`, backed by `colorgrad` presets) or fixed thresholds in `theme.rs`; trend arrows go through the shared `ui::types::metric_cell()` so a `↑` means the same thing in either table (and is visually distinct from the `▲`/`▼` a header uses for sort direction); both the indices and nodes tables shade rows via the shared `ui::types::gradient_position()` (log-scaled against the largest value in the sorted column) so a row's color means the same thing in either panel — keep new data-driven coloring consistent with one of those two mechanisms rather than inventing a third.

**The tables build only the rows that are on screen.** `IndicesTable`/`NodesTable` receive the full visible slice *and* a row offset, and turn only `visible[offset..offset + visible_row_capacity(area)]` into `Row`s. This is load-bearing at scale: each row clones two strings and formats three numbers, so building all of them cost ~93ms per frame on a 50k-index cluster against ~0.26ms for the window (the event loop redraws unconditionally ~20x/sec, so that latency landed on every keypress). Never map over the full slice to build rows. Two things still have to consider the *whole* visible list rather than the window: the row count in the title, and the gradient's `max_value` — normalising the gradient against the window would make a row change color as you scroll past it.

**Scroll offsets are computed by `ui::scroll_offset()`, not by ratatui.** Handing `Table` only the visible window means it can no longer scroll to reveal a selection, so `draw` computes the offset itself and passes the selection *relative to the window*. `ui::visible_row_capacity()` is the single source for "how many rows fit" — the tables, `draw`, and `table_page_size` all use it, and if they disagreed, paging would skip or repeat rows.

**The tables' scroll offsets live in `App.table_offset` / `App.node_table_offset`, not in the widgets.** `ui::draw()` takes `&mut App` for exactly this reason: it computes each frame's offset with `ui::scroll_offset()` from the *previous* frame's offset and the selection, renders, then writes it back. Carrying the offset is what makes the table scroll only when the cursor would leave the viewport. `ui/table.rs` must therefore *not* compute an offset from the selection itself (an earlier version re-centered the selection every frame, which pinned the cursor and slid the whole list under it on every keypress).

Popups (`details_popup.rs`, `help_popup.rs`) each expose their own sizing (`visible_rows`, `max_scroll`) derived from the same percentage-of-terminal area they render into, for the same reason as `compute_areas` — so keyboard paging matches what's on screen. Both wrap their text, so `max_scroll` counts *wrapped* rows (`Paragraph::line_count`, ratatui's `unstable-rendered-line-info` feature); `ui::draw` clamps the stored scroll to it each frame so presses past the end aren't banked as dead keys.
